# Архитектура PortSentinel

## Текущее состояние и границы

До работы существовал только README с проектной спецификацией. `cmd/portsentinel` и `cmd/portsentinel-server` — независимые entrypoints одного модуля. `internal/config` управляет YAML/env; `security` разбирает URL, разрешает DNS и проверяет каждый IP; `diagnostics` выполняет регистрацию проверок через `Check`; `server` ограничивает одновременные задачи буферизированным каналом. Ядро не импортирует HTTP API.

Стадии DNS, TCP, TLS, HTTP используют единый context deadline. Проверки TCP и HTTP подключаются к уже проверенному IP. Для HTTPS исходный hostname сохраняется для TLS SNI и проверки сертификата. HTTP client не следует редиректам, не использует системный proxy и читает не больше 4 KiB body. Отчёт JSON версии 1 содержит только технические результаты. Дополнительный check добавляется в `Engine.Checks` без изменения цикла движка.

Серверные адреса всегда проверяются как публичные; разрешены только порты из конфигурации. CLI требует явный `--allow-private` для локальной диагностики. Сервер по умолчанию слушает localhost, API не имеет встроенной аутентификации и требует защиту перед внешней публикацией.

## Ограничения и риски

Один запрос выполняет стадии последовательно, а ограничение concurrency действует на HTTP API. CLI запускает одну цель. DNS ответ с любым запрещённым IP отклоняется целиком, что безопаснее при смешанных ответах. Параметры query передаются HTTP цели, но редактируются в `Report.Target` и исключаются из типичных HTTP ошибок. HTTP response headers ограничены 16 KiB. Ready означает готовность процесса принимать задания: внешней обязательной зависимости нет.
